# Project memory

## Product intent & audience

- Room booking/availability app for students.
- Goal: let students quickly check whether a room is available for a requested time slot and understand why a verdict was reached.
- Explanations target non-technical students: short, plain language, naming the rule and the relevant times.

## Brand personality & voice

- Helpful, concise, student-friendly.
- Explanations are 1–2 sentences; no jargon, no walls of text.
- Honest about rejections: tells the student *why* and suggests next steps (e.g. "Try 12:00 or later").

## Visual design & UX direction

- Verdict currently surfaced via `VerdictBanner.tsx`, which renders the checker's machine reason directly.
- Future: add an optional LLM adapter as a phrasing layer over the verdict, keeping the banner as the fallback.
- Treat LLM output as display text only: escape it, no HTML, no markdown execution.
- Booking titles are user-controlled input and must never affect logic or rendering safety.

## Decisions, constraints & rationale

- **Deterministic checker is the single source of truth.** `bookingLogic.ts` → `checkAvailability` is pure and decides availability. The LLM may only rephrase its reason.
- Verdict shape: `{ available: boolean, reason: string }`.
- Slot times are parsed to minutes-from-midnight (`start`, `end`, `currentMinutes`).
- Room model: `id`, `name`, `blocked`. Booking model: `roomId`, `start`, `end`, `title`.
- Rules (AC1–AC5) in the checker:
  - AC1: reject invalid intervals (`start ≥ end`, or outside 00:00–24:00).
  - AC2: reject durations > 120 min; exactly 120 is allowed.
  - AC3: blocked rooms always rejected.
  - AC4: overlaps rejected; touching endpoints allowed (10:00–11:00 + 11:00–12:00 OK).
  - AC5: check never mutates bookings or rooms.
- AC6 (UX): explanation states which rule fired and the times involved.
- **Authority rule:** LLM cannot flip/invent verdicts or override any rule. If the LLM is unavailable, times out, or contradicts the verdict (e.g. says "available" when verdict is false), discard its text and show the checker's built-in reason. Availability is never affected by LLM failure.
- Flow: `student request → rule engine (checkAvailability) → LLM adapter (optional, rephrase-only) → response`. The engine→response path is unconditional; the LLM branch is additive and disposable, guarded by a contradiction check.
- Validation failures (empty/invalid `current`, `start`, or `end`) produce a validation message, no verdict, and no LLM call.

## Open questions & assumptions

- LLM adapter is specified but not yet implemented; `VerdictBanner.tsx` currently shows the checker's reason as-is.
- Assumption: the contradiction guard detects verdict mismatches via keyword/phrase checks (e.g. "available"/"unavailable") — exact mechanism not yet defined.
- Assumption: response locale is English for now; multilingual phrasing not addressed.
- Unresolved: whether the adapter call is async with a hard timeout, and what timeout value to use.
- Unresolved: whether suggestions like "Try 12:00 or later" are generated by the checker's reason or added by the LLM adapter.
